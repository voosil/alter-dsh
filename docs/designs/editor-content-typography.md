# 正文排版：规则与依据

这篇方案说明文档正文内容区按什么规则排版，以及这些规则凭什么定。它只覆盖正文内容区；壳层、工具栏、
slash 菜单、评论轨与历史面板的视觉仍按[编辑器还原验收](../acceptance/editor-experience-p0-p6.md)冻结。

## 冻结范围的收缩

- **决策**（2026-11-12 产品授权）：正文内容区的排版解冻，由本篇管理；编辑面其余部分继续冻结。
- 边界：`Editor.module.css` 里 `.surface` 之下的内容规则（排版与块级外观）可改；
  `.floating`、`.toolButton`、`.slashMenu`、`.linkBar`、`.wordCount` 等浮层与工具栏规则仍冻结。
- 内核的结构归一化（`kernel.css`）不变：它只中和 ProseMirror 多出来的一层包装，不引入视觉语言。

## 为什么不能整包引入

社区里被当作「通用编辑器样式」传播的东西分四层，可移植性差别极大：

| 层 | 解决什么 | 代表 | 能否整包替换 |
| --- | --- | --- | --- |
| ① 阅读排版 | 标题阶梯、段距、行宽、行高 | Tailwind Typography、github-markdown-css | 能，但只覆盖文字 |
| ② 块级视觉 | 引用、代码、表格、任务、块选中 | BlockNote、Milkdown、ProseMirror | 不能：与自身组件、DOM 契约绑定 |
| ③ 中文处理 | 中西文混排、标点挤压、每行字数 | heti（赫蹏） | 能，纯 CSS + 可选脚本 |
| ④ 主题与令牌 | 颜色、圆角、语法高亮如何参数化 | Tailwind prose 变量、Radix、open-props | 只能借做法 |

真正「自带完整正文视觉语言」的只有 BlockNote、Milkdown Crepe、Lexical playground 三家；
Tiptap 官方、ProseMirror 基线、Editor.js 核心在正文排版上是空的（这是事实，不是没收全）。

| 候选 | 许可 / 规模 | 能给我们什么 | 为什么不整包用 |
| --- | --- | --- | --- |
| Tailwind Typography | MIT、2548 万周下载 | 唯一写全的数值表：em 相对间距、相邻抑制、表格只留横线 | 需 Tailwind 构建链，不是可引入的 CSS |
| github-markdown-css | MIT、45.3 万周下载 | 单类名作用域、`p{margin-bottom:10px}` 与我们同值 | 1248 行的冷灰蓝 GitHub 主题，引入等于重上色 |
| Milkdown Crepe | MIT、57.6 万周下载 | 每主题只含变量的 `style.css`；引用圆头竖条；暖纸色板 | 主题绑定 Crepe 组件类名 |
| BlockNote | **MPL-2.0**、94.5 万周下载 | 3em/2em/1.3em 标题阶梯、定宽 marker 槽、padding 代替 margin | 选择器绑自身 `data-content-type`；文件级 copyleft |
| heti 赫蹏 | MIT、1.58 万周下载 | 中文排版规范：42em 行宽、两端对齐、引用浅底色块 | 行高 1.5 与我们 1.9 是两套节奏；增强脚本要改文本节点 |
| Radix Colors / open-props | MIT | 按用途绑定的 12 步色阶；`:where()` 零特异性 | 冷灰高饱和色板，与暖中性令牌不兼容 |
| Novel / Editor.js | Apache-2.0 | 只作对照样本 | Novel 停更且正文样式全来自 Tailwind；Editor.js 核心无正文规则 |

## 现基线与主流取值的差距

| 维度 | 改造前 | 主流取值 | 判断 |
| --- | --- | --- | --- |
| 行宽 | 700px ≈ 43.5 字/行 | clreq 常见 17–40 字、上限 48 字 | 在上限内，高于书籍舒适区约 3.5 字 |
| 行距 | 14.4px = 字号的 90% | clreq 50%–100% | 在区间内，靠松端 |
| 段间距 | 10px | GitHub 10px、prose 20px | 与 GitHub 同值 |
| h1 | 22px | 26–48px | 偏小，且与 32px 文档标题只差一档 |
| h2 | 18px | 20–27px | 偏小 |
| h3 | 16px（= 正文） | 20–22px | **与正文同号，三级标题实际不存在** |
| 标题间距 | 写死 30/28/20px | em 相对字号 / 1.5× 字号 | 没有可推导的阶梯 |
| 引用 | 1px 边框、零内距 | 2–4px 边框或浅底色块 | 全表最弱的一处 |
| 列表缩进 | 1.2em（19px） | 1.6–2em | 偏窄，符号与折行文字贴太近 |
| 表头底色 | `--alter-surface-nav` | 可辨识的表头带 | 与白底几乎同色，表头读不出来 |

数据来源：npm registry 与 GitHub API（取数 2026-11-12）、[W3C clreq 中文排版需求](https://www.w3.org/TR/2026/DNOTE-clreq-20261104/)、
各仓库源码。候选的完整清单、逐条数值与许可细节见 git 历史（调研结论已压缩至本篇）。

## 排版的角色与阶梯

正文 16px / 行高 1.9 不变（clreq 下字号的 90% 行距落在 50%–100% 区间内）。标题阶梯以正文字号为基准、
用 `em` 表达，改字号时整条阶梯自动跟随：

| 角色 | 字号 | 与正文比 | 用途 |
| --- | --- | --- | --- |
| 文档标题（输入框） | 32px | 2× | 壳层，不在本篇范围 |
| h1 | 26px | 1.625× | 章节 |
| h2 | 22px | 1.375× | 小节 |
| h3 | 18px | 1.125× | 条目 |
| h4 | 16px | 1× | 靠字重区分 |
| h5 / h6 | 14px | 0.875× | 靠字重，h6 再降一档色调 |
| 正文 | 16px | 1× | — |

- 标题统一 600 字重、行高 1.3、零字距；上间距恒大于下间距（约 32 / 29 / 24 / 22 / 21px）。
- 理由：原阶梯 h1 22 / h2 18 / h3 16 的核心问题是 h3 与正文同号；同时 32px 文档标题与 22px h1 之间
  只有一档。新阶梯让相邻角色至少差 1.125×，并让标题与它所统辖的段落靠得更近。
- 被否：h1 提到 28–36px。28px 与 32px 的文档标题只差 4px，会让「章节」与「文档名」混淆；36px 是
  整篇标题的量级，与页头重复。
- Markdown 粘贴与 Agent 写入会带来 h4–h6（slash 菜单与文本类型菜单只给 h1–h3），因此也必须显式定规则，
  否则会落到浏览器默认的 1em 粗体配 21px 外边距。

## 块级外观

| 块 | 决策 | 理由 |
| --- | --- | --- |
| 段落 | 保持 10px 下间距 | 与 github-markdown-css 同值 |
| 引用 | 左内距 16→20px，文字降为 `--alter-text-secondary` | 靠色深拉开层级，而不是把彩色边框加粗 |
| 列表 | 缩进 1.2em→1.6em | 1.2em 在 16px 下只有 19px |
| 表头 | 底色 `--alter-surface-nav`→`--alter-surface-hover` | 原底色与白底几乎同色 |
| 选区 | 透明度 0.08→0.12 | 原选区在浅色正文上几乎不可见 |

被否：引用改成 4px 圆头竖条（Milkdown 式）或浅底色块（heti 式）。前者要新增伪元素，与块悬停已有的
`::after` 高亮挤在同一元素上；后者需要一个本产品没有的引用底色令牌。
被否：给标题加 `text-wrap: balance`、给段落加 `text-wrap: pretty`。它们会在编辑态每次击键时重排折行，
标题与段落的视觉断点在输入过程中跳动；静态页面值得，可编辑正文不值得。

## 刻意不改的三处

- **行宽 700px**：clreq 下行长常见 17–40 字、上限 48 字，当前约 43.5 字/行——在上限内但高于舒适区。
  压到 40 字需约 644px，会连带挪动正文栏与评论轨的关系，收益不抵。
- **行高 1.9**：偏离主流（1.5–1.8）但是有意识的选择，且落在 clreq 区间内。
- **代码块不加语法高亮、不做暗色主题**：前者要新增依赖并进入客户端 bundle，后者要新增整套暗色令牌；
  两者都是独立变更，不属于排版范围。

## 风险

- 内容规则与浮层规则同处一份 CSS Modules 样式表，diff 相邻；评审须确认 `.floating` 及其后的规则未被触碰。
- `em` 间距依赖 `.surface` 的 16px。将来若改正文字号，间距与阶梯会整体跟随，这是预期行为；
  但容器级缩放（改根字号）不影响 `em`，两种做法不要混用。
- 标题阶梯是 em 表达，若某天给正文加「小/大字号」偏好，整条阶梯会跟着缩放，需一并复查间距观感。
