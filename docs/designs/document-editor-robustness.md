# 即时编辑器健壮性：方向与分阶段改造范围

这篇方案回答「即时编辑器的健壮性为什么按系统保障来做、分几个阶段改、每阶段的范围与边界」。
验收标准以[验收清单](../acceptance/document-editor-robustness.md)为准，本篇不复制条目；内容架构
与写入契约以[内容架构方案](document-content-architecture.md)和
[Operations 规范](../specs/document-operations-v0.md)为准。

## 1. 判断

- **功能面已可用，系统面部分落地**：编辑器内部的输入、撤销与渲染由 ProseMirror 承担，是稳的；
  P0 保存生命周期（自动保存/草稿/失败重试/冲突和解/大变更分段）、P2 评论与历史、P5 Agent 块级 patch
  已部分落地；仍缺的是双入口并发、版本恢复脏状态、输入层极限、观测与规模回归。
- **底座不换**：Tiptap/ProseMirror 已是专业底座，换编辑器不会自动带来草稿、重试、合并与观测能力。
  缺口在编辑器之外的系统层，重写编辑面是无效投入。
- **参考坐标系不是某个实现**：商业级产品（Google Docs、Notion、Yjs/ProseMirror 生态）提供的是
  保证——不丢数据、可收敛、可观测；此前 dsh-nook 的编辑器提供的是输入层补丁经验。两者都只作参考，
  验收基线是本仓库的验收清单。
- **验收原则**：每条失败路径都有兜底与回归测试，而不是「零 bug」。

## 2. 目标与非目标

**目标**

- 输入不丢：未保存内容在切换、崩溃、并发与重试下都可恢复或明确告知。
- 失败可恢复：任何保存/加载失败都保留本地内容并给出下一步，不以「重新加载」作为唯一出口。
- 并发可收敛：人与 Agent 同时写入时保留双方修改，冲突有对比、合并或另存路径。
- 输入保真：IME、粘贴、拖放与媒体输入不静默丢内容，不安全内容不进入文档。
- 保存可行：变更规模不因单批操作上限或模型上限变成死路。
- 规模可预期：上限文档的加载、输入与保存在明确预算内；异常可观测、可回归。

**非目标**

- 不做多人实时协同（CRDT/OT 服务端）与 presence。
- 不做多端同步与移动端编辑。
- 不替换编辑器底座，不重写 AST/Operations 契约（新增 op 必须先升 spec）。
- 不做独立离线客户端；离线只覆盖「本地输入不丢、恢复后同步」。

## 3. 分阶段范围

| 阶段 | 目标 | 范围 | 明确不做 | 验收条目 |
| --- | --- | --- | --- | --- |
| 0 保存生命周期 | 不丢数据、存得下 | 草稿与自动保存、离开与崩溃恢复、保存期间输入保留、保存不重建编辑面、幂等重试、大变更分段提交 | 不改 Operations 契约；不做合并 UI | A、C1、C2 |
| 1 并发与恢复 | 人与 Agent 冲突不再是唯一下场 | 冲突时保留草稿 + 对比/合并/另存最小闭环；双入口与版本恢复的脏状态保护；标题与正文双写一致 | 不做实时协同与 presence | B、E3 |
| 2 输入层 | 真实输入不丢字、不丢内容 | 粘贴/拖放/图片上传管线与清洗；IME 与组合输入；空块与空列表项语义；键盘与无障碍 | 不做任意 HTML 的无损导入 | C3、C4、D1–D3、D5 |
| 3 正确性与观测 | 异常可兜底、可诊断 | 只读降级与错误边界；撤销语义统一；锚点失效标记；日志、遥测与故障注入入口 | 不建全量可观测平台 | D4、E1、E2、E4 |
| 4 规模与回归 | 上限文档不退化成 bug 现场 | 性能预算与基线测量；分段保存的规模验证；映射与操作序列 fuzz；浏览器级用例矩阵 | 暂不做虚拟化或分页渲染，先测再定 | F、G |

阶段顺序的理由：阶段 0 先消除数据丢失与保存死路（收益最大、风险最低）；阶段 1 处理本产品特有的
人+Agent 并发；阶段 2/3 才处理输入与异常这类体验问题；阶段 4 用预算与回归把前三个阶段锁住。

当前进度：阶段 0 的保存生命周期、阶段 1 的冲突保留与标题/正文一致、阶段 2 的粘贴与媒体输入、
阶段 3 的锚点失效提示已落地；双入口、版本恢复脏状态、IME/空块极限、观测与规模回归仍按清单推进。
逐项状态以[验收清单](../acceptance/document-editor-robustness.md)为准。

## 4. 关键决策

- **保留三层结构**：Tiptap 编辑面、JSON AST 权威、Operations 写入通道在本次改造中都不替换。
- **客户端先行**：草稿与待提交批次先落本地，网络或宿主异常不阻塞继续编辑。
- **复用幂等能力**：Host 已支持幂等重放，客户端需持久化幂等键并在重试时复用，避免「已提交但回执
  丢失」被误报为冲突。
- **冲突解决顺序**：先做「保留 + 对比 + 另存」最小闭环，再做块级三方合并；CRDT 不在本范围。
- **大变更兜底优先客户端分段**：按可独立提交的批次分段并显示进度；只有段落语义不可拆时才评估
  新增整篇事务能力，且先升 spec。
- **输入降级可见**：schema 不支持的粘贴内容降级为可见占位或提示，不静默丢弃。
- **失败可见**：任何保存/加载失败必须保留本地内容并给出下一步动作。

## 5. 开放决策

- 草稿的多标签共享策略：草稿按文档落本地存储，跨窗口广播未设计。
- 冲突合并交互：当前只提供保留草稿 + 重试/重载，块级对比与合并 UI 未做。
- 性能预算数值与基准机器：验收清单中的暂定数值在阶段 4 锁定。
- 验收清单何时从 `draft` 转 `active`：P6 复验通过后转，之后滚动验收。

## 6. 风险与依赖

- **协议改动面**：涉及 Host 协议的改动（大事务、资产通道等）必须实现、规范、测试同变更，
  必要时升版。
- **写频率上升**：自动保存会放大写入与版本记录，需复核版本裁剪与备份策略，避免本地库膨胀。
- **交互成本**：合并 UI 是最大不确定项，先用最小闭环验证真实冲突频率，再决定投入。
- **回归基建**：浏览器级 IME、粘贴与故障注入需要先搭，否则「修好又回归」概率高。
- **体量约束**：新增第三方库必须打进客户端 bundle，选型前先评估产物大小。
