# 空间部署形态：本地权威与自部署服务端

## 问题

Space 作为开源的 DSH 插件交付，每个用户自己使用：默认本地安装即可用；希望多设备访问的用户可以把它部署到自己的服务器。现有实现只有本地权威一种形态（Host 进程 + SQLite），远端形态没有定义，容易把「服务器在线」与「本地化 + 同步」当成二选一，并围绕离线、鉴权、工作区语义反复推翻方案。

## 结论

同一个插件、同一套协议支持两种权威形态，模式由配置选择，不拆成两个产品：

- **本地模式（默认）**：数据落在用户本机 DSH 的 `~/.dsh/data/space`；离线可用；保留「空间 ↔ 工作区」映射。
- **服务端模式（可选）**：用户在自有服务器部署独立的 Space 服务；插件作为客户端在线访问；多设备共享同一权威；不建本地 DSH 工作区。

两种模式之间不自动同步；迁移是一次性、显式的数据目录搬迁。

## 模式边界

| 维度 | 本地模式 | 服务端模式 |
| --- | --- | --- |
| 数据权威 | 本机 DSH Host 的 SQLite | 独立 Space 服务端的 SQLite |
| 离线 | 可用 | v1 不可用（在线） |
| 多设备 | 单设备 | 同一服务端的多设备在线访问 |
| 空间 ↔ DSH 工作区 | 保留现有映射 | 不映射（工作区是宿主/设备本地概念） |
| 空间目录 | 本机宿主选择器 | 服务端目录：远端浏览或手工输入，不使用本机选择器 |
| Agent 工具 | 本地直连业务服务 | 本地转发到服务端，工具契约不变 |
| 备份责任 | 用户本机快照 | 服务端快照 + 用户自行异地复制 |
| 鉴权 | 宿主自带 | 单用户设备 token |
| 迁移 | — | 停服拷贝 `space.db` 与 `assets/`（两个方向） |

## 关键决策

### 两种模式共用一个插件与协议

服务端模式只改变权威实现与传输，不改变客户端 UI、工具契约与写入语义。理由是开源交付只有一条安装路径、用户可以无感切换，实现也不必分叉。被否：拆成「本地版」与「服务器版」两个插件。

### 服务端是独立服务，不依赖 DSH

服务端只需 Node + SQLite 与业务代码即可运行。理由是自部署成本低、无需把 Agent 与文件系统搬上云、攻击面更小。被否：把整机 `dsh web` 作为产品形态（适合临时验证，不是交付形态）。

### Agent 工具在服务端模式下由本地 Host 转发

工具仍在本地 DSH 注册，模型看到的契约与本地模式一致，仅把调用转发到服务端。理由是用户应仍能在本地 Agent 中读写自己的空间，且工具说明与提示词不需要分叉。被否：只允许服务端 Agent 访问空间（本地 Agent 失去能力，与产品预期不符）。

### 服务端模式不建本地 DSH 工作区

空间目录属于服务器，映射到本机工作区没有稳定语义：路径、权限与「同一目录只归属一个空间」的约束都跨不上机器。被否：把远端路径映射成本地工作区。

### v1 不做离线缓存与多设备合并

本地模式已经覆盖「离线 + 单设备」的需求；服务端模式定位为在线多设备共享。同步与冲突合并是量级更大的工程，等确有「同一用户多设备离线编辑」需求，再以本地缓存 + 写队列演进。被否：首版就做本地权威双向同步或 CRDT。

### 鉴权保持单用户设备 token

自部署用户是单用户，账号体系不是当前产品需求；设备 token 存 DSH credentials，服务端可撤销与轮换即可。被否：引入账号与多租户（注册、找回、权限模型都超出产品定位）。私网（如 Tailscale）只降低网络暴露与传输风险，不替代 token。

### 服务端以 Docker 交付

单容器运行、数据目录挂卷、配置经环境变量或挂载的 env 文件提供。理由是自部署用户最熟悉、跨平台差异最小、升级与回滚可预期。被否：只提供 Node 源码运行（要求用户自己装依赖、配守护进程）。

### 配置入口与 Agent 可配置

设置页新增「服务器」区：模式（本地/服务端）、服务器 URL、token、连接状态与测试、切换与迁移提示；token 只显示「已配置」并存 DSH credentials。Space 的业务设置（服务器连接、存储策略、模式）统一走 Host 侧设置接口，Agent 通过模型工具读写同一接口，因此可以在对话里完成客户端配置。写入服务器目标或 token 属于敏感操作，需要用户确认并记审计，不能静默改。仓库同时提供 Docker 部署资产与部署引导，Agent 只向用户索取必要信息（服务器地址与访问方式、平台、是否公网/私网），完成服务端部署、健康检查、客户端配置与可选迁移，失败可回退本地模式。被否：只靠手改 profile 配置（用户不可发现，Agent 也无法安全写入）。

### 服务端模式的目录选择

空间目录使用远端目录浏览 + 手工输入，不使用本机原生选择器：原生选择器返回本机路径，与服务端语义不符。被否：把本机目录路径写入服务端空间。

### 迁移用停服拷贝数据目录

本地与服务端使用同一数据格式（数据库 + 资产目录），停服后整体拷贝最可靠，也复用现有快照与恢复流程。被否：首版做在线导入导出界面。

## 服务端要求（产品约束）

- 独立启动：不需要 DSH 运行时；以 Docker 镜像交付，单容器 + 数据卷，配置经环境变量或挂载的 env 文件提供；源码运行只用于开发调试。
- 传输与安全：HTTP(S) + token；默认只监听本机或内网，公网部署要求 TLS 反向代理或私网（如 Tailscale），不暴露未经鉴权的端口。私网只降低网络暴露与传输风险，不替代应用鉴权：token 仍必需，否则任何能连上该端口的进程或 tailnet 设备都直接拥有全部空间权限。
- 运维：健康检查、协议版本探测、每日快照与备份/恢复说明随服务端一起交付。
- 兼容：插件与服务端共享协议版本，不匹配时给出明确错误，不静默失败。

## 后续演进：本地缓存与写队列

编辑面是本地状态，击键不经过网络；服务端 RTT 只影响保存回执、打开文档与图片加载。因此缓存与队列不是输入性能修复，而是解决弱网/断网下的保存可靠性、首次打开与图片的感知延迟。

- **写队列**：由本地 Host bridge 持有待提交操作，按文档串行、带幂等键与 `baseRevision`，重连后重放；确认必须发生在队列落盘之后，UI 区分「已保存到本地（待同步）」与「已同步」；业务冲突不自动重试，转为草稿或版本。
- **读缓存**：资产按内容寻址，可长期缓存；文档与列表按 revision 做 stale-while-revalidate，并明确提示可能过期。
- **边界**：服务端仍是唯一权威；不上 CRDT/OT（单用户多设备，冲突用 CAS 与版本兜底）。
- **触发**：先用延迟注入与真实网络测量保存 P95、打开耗时；达到阈值或用户明确提出离线编辑再排期。当前浏览器草稿写 localStorage，与「浏览器不落业务数据」的约束有张力，做缓存与队列时一并收敛。

## 被否方案

- **云盘或 NAS 直接同步 `space.db`**：SQLite + WAL 不是同步安全格式，锁、半写与冲突副本会丢数据。
- **客户端直连远端 DSH `/api`**：桌面页面是自定义协议页面，跨源与 Host/Origin 鉴权不成立，素材路由也无法携带凭据。
- **整机 `dsh web` 上云作为正式形态**：能零代码验证多设备体验，但 Agent、终端与文件都在远端，且不是 desktop 面板。

## 开放问题

- 设备 token 粒度：单服务端 token 还是每设备独立 token；v1 可先单 token，轮换与撤销后置。
- 是否提供免 token 的私网模式（例如信任 Tailscale Serve 注入的身份头）：v1 不做，避免把应用鉴权寄托在网络配置上。
- Agent 写入服务器配置的确认形态与审计呈现：设置页与对话共用一套确认，还是对话走审批、设置页走即时写入。
- 对话式部署的入口形态（随插件分发的引导流程还是设置页一键入口）与失败回退体验。
- 模式切换的运行时语义：切换是否需要重启 Host，切换时旧数据的保留、迁移与回退提示如何呈现。
- 本地缓存与写队列的存放位置与 spec 落点：Host bridge 的缓存目录，还是沿用现有浏览器草稿；首个版本先做哪一层。
